# Private attachments

Phase 11 application code is implemented. Provisioning and real R2 acceptance remain open; unit and disposable PostgreSQL tests do not certify provider behavior. The application never needs a public bucket or public delivery domain.

## Environment setup

1. Create separate private R2 buckets for development, preview and production. Keep both the `r2.dev` public endpoint and custom public domains disabled. Previews must use their own bucket and credentials.
2. Create an Object Read & Write API token restricted to the single environment bucket. Store its S3 access key and secret only in that environment's server secret store. The runtime needs HEAD/GET/PUT/DELETE, not bucket administration. Keep backup access separate.
3. Configure `R2_ENDPOINT`, `R2_BUCKET`, `R2_ACCESS_KEY_ID`, and `R2_SECRET_ACCESS_KEY` as described in [ENVIRONMENT.md](ENVIRONMENT.md). The endpoint is the account S3 endpoint, including the jurisdiction subdomain when applicable. Configuration is checked lazily when storage is used, without echoing values. Core pages/builds need no R2 credentials.
4. Configure bucket CORS separately with an administrative account. Replace the example origin below with that environment's explicit approved origins (`R2_CORS_ORIGINS` is an operator inventory value, not a runtime CORS installer). Do not use `*` or share production and preview origins.

```json
[
  {
    "AllowedOrigins": ["https://example.invalid"],
    "AllowedMethods": ["PUT", "GET", "HEAD"],
    "AllowedHeaders": ["Content-Type", "If-None-Match"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 600
  }
]
```

Cloudflare documents [presigned requests](https://developers.cloudflare.com/r2/api/s3/presigned-urls/), [atomic conditional PUT support](https://developers.cloudflare.com/r2/api/s3/api/), and [bucket CORS](https://developers.cloudflare.com/r2/buckets/cors/). The adapter uses the AWS S3 SDK with region `auto`, explicit content-type/conditional-header signing, and optional checksum behavior disabled. Browser and agent transfers must send the exact returned headers. Do not strip `If-None-Match: *` or replace conditional writes with ordinary PUTs.

## Service and HTTP flow

`createAttachmentService` is shared by HTTP and future MCP tools; provider calls are isolated in `src/server/integrations/r2.ts`. Every operation checks ownership, target project grants and the required scope. Metadata omits object keys and credentials. Mutations record activity transactionally. File removal requires the owner session; agents cannot permanently remove files.

| Operation | HTTP | Scope/input |
| --- | --- | --- |
| List target files | `GET /api/v1/attachments?kind=task&id=<UUID>&limit=50&cursor=<UUID>` | `read`; kind can also be project/section; maximum page size 100 |
| Begin | `POST /api/v1/attachments` | `upload`; `{ input: { kind, id, originalName, declaredMediaType, declaredSize } }`; `Idempotency-Key` required |
| Finalize | `POST /api/v1/attachments/<UUID>/finalize` | `upload`; `{ input: {} }`; intrinsically idempotent once ready/failed |
| Download instructions | `GET /api/v1/attachments/<UUID>/download` | `read`; returns `{ url, expiresAt }` only for ready files |
| Stable note/download link | Same download route with `?redirect=true` | Reauthorizes every visit, then redirects with private/no-store and no-referrer headers |
| Remove | `POST /api/v1/attachments/<UUID>/remove` | Owner only; `{ input: { expectedRevision } }`; `Idempotency-Key` required |

Browser writes require the application origin. Agents use a scoped bearer credential without a browser session. Begin returns `{ attachment, upload: { method: "PUT", url, headers, expiresAt } }`. Upload raw bytes directly to that URL; no binary/base64 payload passes through the application or MCP. Retry an uncertain begin with its original input/key; the same record, immutable key and original expiry are retained. A replay after verification/expiry returns `upload: null`.

Upload instructions last at most ten minutes. Downloads last five minutes and always use `attachment` disposition, a sanitized ASCII fallback plus UTF-8 filename, verified media type and private/no-store. Store the stable application link in notes, never an expiring storage URL. Links are references only; moving or copying a note does not grant file access. Removing a file breaks its note links.

## Verification and cleanup

The finalizer claims `pending → verifying` in a short transaction, releases locks, then HEADs the actual object and inspects bytes using its ETag as an `If-Match` condition. It rejects actual size above 20,000,000 bytes, declared-size/content-type mismatches, content encodings, bad image/PDF signatures, invalid UTF-8/binary text and invalid JSON. Images/PDFs receive bounded signature inspection; text is inspected completely within the size cap. This is format validation, not a malware scanner or a full image/PDF decoder. All types are downloaded as attachments.

A final short transaction reauthorizes and checks the verification revision before recording ready metadata/activity. Overlapping verification returns a retryable conflict. A verifier interrupted for 60 seconds can be reclaimed; its old revision cannot commit. Transient provider errors retain a pending retryable record. Missing/invalid/expired uploads become failed, cannot download, and queue cleanup. An already-uploaded object may finalize after PUT expiry until the cleanup safety margin ends. Failed uploads use a new initiation/key when the user selects the file again; bytes are never replaced under an existing key.

Presigned PUT is not an S3 POST size policy: oversized bytes can temporarily reach R2. Finalization rejects them and durably schedules their deletion. Pending/failed files, stale verifiers and permanent target/file removal retain immutable keys in PostgreSQL jobs. Deletion waits until PUT expiry plus one hour so a still-valid upload URL cannot recreate removed bytes. Failed cleanup remains retryable through the durable job runner. Abandoned-upload cleanup fences verifiers and skips ready files. Failed metadata stays visible for Retry with file/Remove; it is not a successful attachment.

As in Phase 10, jobs run in bounded Next.js `after()` batches after authenticated requests. With no application traffic, cleanup waits for the next authenticated request; no cron or external scheduler was added.

## Real R2 acceptance still required

Use a disposable nonproduction bucket and synthetic files. Record the environment, date and results without credentials or signed URLs:

- Confirm public access is disabled and a fresh URL performs a successful approved-origin CORS preflight with exactly `Content-Type` and `If-None-Match`.
- Upload/finalize/download from desktop, mobile and a local agent using the returned headers and scopes. Check unauthorized target/grant/owner and revoked-key failures.
- Reuse a successful PUT URL with different bytes; require 412 and unchanged verified bytes. Race two first writes; at most one may succeed. Removing/changing the signed conditional header or content type must fail signature validation.
- Exercise missing, wrong-signature/type, invalid UTF-8, oversized actual bytes, expired PUT, expired GET and provider outage cases. None may yield a successful download of a non-ready file.
- Allow the upload URL and safety margin to expire; run normal authenticated requests and verify rejected/abandoned/removed objects disappear, retries survive a provider failure, and ready objects remain. Verify permanent target deletion still cleans its bytes after metadata cascades.

Do not mark the phase's provider exit gate complete until these checks and environment isolation are verified against R2.
