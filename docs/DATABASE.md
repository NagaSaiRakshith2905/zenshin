# Database implementation

Phase 2 implements the model in [SCHEMA.md](SCHEMA.md); product behavior remains governed by the specification. No database migration, seed, integration test, auth handshake or provider check has been executed. Generated migrations have been reviewed as SQL artifacts only. Verification remains deferred.

## Schema and tooling

`src/server/db/schema/` contains the generated auth model and six domain modules: `identity`, `work`, `context` (notes/activity), `files`, `github`, and `operations`. The barrel is the sole Drizzle Kit schema input. The initial SQL and snapshot/journal in `drizzle/` are generated by the pinned Drizzle Kit. Preserve all three artifacts in source control. Never use schema push or run migrations at application startup.

| Command | Purpose |
| --- | --- |
| `pnpm db:auth:generate` | Regenerate auth/plugin definitions offline, then normalize generated Date columns to `timestamptz`. Review changes before generating SQL. |
| `pnpm db:generate` | Generate a forward migration/snapshot from the schema, offline; no URL required. |
| `pnpm db:migrate` | Apply committed migrations using `DATABASE_MIGRATION_URL` only. Requires the intended environment's unpooled URL. |
| `pnpm db:seed` | Insert the deterministic development graph into local `zenshin_dev` using `DATABASE_URL`. |
| `pnpm db:fixture:perf` | Insert the separate performance dataset into local `zenshin_perf` using `DATABASE_URL`. |

Database commands except auth generation load an optional ignored `.env.local`; already-exported environment variables take precedence. Seeds require `APP_ENV=development`, reject production/test runtimes, remote hosts, URL overrides, and any database name other than their exact local target. Provision the empty database and apply migrations separately before loading a fixture. Seeds are one atomic insert, refuse duplicate IDs, and never truncate/reset/upsert existing work. Recreate the disposable database deliberately to reload; there is no destructive reset command.

The development graph has 2 projects and 32 tasks: all six workflow categories, three section levels, project-root work, one subtask level, completed/empty/all-canceled sections, due dates on either side of the fixed fixture date, independently archived descendants, unresolved parent work with finished leaves, canceled and effectively archived Done prerequisites, labels, all seven property types (including false Checkbox and Multi-select), notes, note revisions and activity. Time is fixed at `2026-10-29T00:00:00Z`. The performance graph has exactly 50 projects, 10,000 tasks and 50,000 activity records, plus representative context. Inserts are batched to bound PostgreSQL parameter counts. No performance measurement is claimed.

Both graphs use a synthetic `example.invalid` owner with no provider account, session or key. They do not provision the real owner or permit login. They contain no actual attachment bytes, GitHub provider data or secrets. Tests can supply an independent namespace to the same pure fixture builder.

`createDatabase()` creates an explicit small, transaction-capable `pg` pool; importing the schema opens no connection. Scripts/tests close it in `finally`. Application callers import the `server-only` database entry point; the connection module is also usable by Node scripts. Phase 4's server entry point must manage the reused app pool and Vercel lifecycle; no route or singleton connects during builds.

## Generated authentication identifiers

Auth `1.7.14`, Better Auth `1.7.14` and `@better-auth/api-key` `1.7.14` generate `user`, `session`, `account`, `verification`, and `apikey`. Keep these singular exports/SQL identifiers. The Drizzle adapter takes the generated schema object with `provider: "pg"`, default singular model names and no custom field mappings. For example, the JS property `session.userId` maps to SQL `user_id`; `apikey.referenceId` maps to `reference_id`, not an invented `user_id` column. Auth primary/foreign IDs remain generated text identifiers; application entities use UUIDs. No organization plugin is enabled.

`scripts/auth-schema.config.ts` is generation-only, without a database or login routes. Phase 3 must reuse its schema-affecting options (`apiKey`, user references, sessions from API keys disabled), alongside actual secure owner-only runtime configuration. Generation requires no secret. `auth.generated.ts` is produced by the CLI and a scripted timestamp-type normalization, with no manually added auth columns. The adapter accepts Date values for these UTC instants. The generated API-key reference is intentionally not a foreign key. Phase 3 must validate that its `referenceId` matches the credential owner before issuing/accepting a credential, and never trust plugin permission/metadata as domain grants.

The written unit mapping test compares configured core/plugin models and field properties to generated Drizzle definitions and UTC types. It has not been run; live adapter behavior remains a Phase 2 Verification item. References: [Better Auth generation](https://better-auth.com/docs/concepts/cli), [Drizzle adapter](https://better-auth.com/docs/adapters/drizzle), [API-key plugin](https://better-auth.com/docs/plugins/api-key), [Drizzle generation](https://orm.drizzle.team/docs/drizzle-kit-generate).

## SQL-enforced invariants

| Area | Database guarantees |
| --- | --- |
| Identity | User preferences have one user; credentials have unique nullable plugin key mappings; scopes contain only known scope names and are nonempty; explicit project grants are unique and owner-matched. |
| Common | UUID application IDs; generated-compatible text auth IDs; UTC event timestamps; date-only due/target/property dates; bigint ordering; positive integer revisions on mutable domain records. |
| Projects/workflows | Prefix format and owner-local uniqueness; positive next counter and task numbers; unique project-local task numbers; at most one default status per project, constrained to Backlog; categories are fixed enums. |
| Work relationships | Composite foreign keys constrain projects, section parents, task parents/sections/statuses, labels, properties/options/values, dependencies and grants to the same owner/project. Direct self-parenting and self-dependency fail. Both dependency directions are indexed. |
| Labels/properties | Unique normalized name keys in each project/definition; unique task-label and task-dependency pairs; unique scalar task/definition value and task/option selection; exactly one non-null scalar value column; selected options belong to the definition/project. Deleting an option also removes selected values. |
| Notes/files | Exactly one target per note/attachment; same-owner target foreign keys; at most one note per target; unique note/revision numbers; unique file object keys, declared size cap, and required ready-file verification metadata/size cap. Failed uploads may retain oversized actual-size metadata for diagnosis/cleanup. |
| Attribution | Agent actors reference an owner-matched durable credential; human actors identify the owner. Activity and note revisions record actor kind/identity; system attribution remains explicit. |
| GitHub | Stable provider IDs and unique repository item numbers; owner-matched installations/repositories/items/task links/imports; unique task/item links and project/item import provenance; rule target FK includes its stable category, and rule-kind checks prohibit wrong-category/Done targets; evaluation event deduplication; unique sync resource and webhook delivery. |
| Operations | Unique job deduplication keys; nonnegative attempts; running jobs require lease token/expiry, and other states have neither; actor/operation/idempotency-key uniqueness and human/agent actor identity matching; ready exports require an object key and completion time. |

Indexes cover scoped task order/status/dates/updated time, section traversal, exact task references and normalized names, association reverse lookups, note/file targets, numeric/date/select property filters, full-text expressions over names/titles/descriptions/note text/property text, activity timelines, repository membership, sync schedules, jobs/leases and expiry scans. Search queries must use the same `to_tsvector('simple', ...)` expressions. Property URL rows share the text storage/index; the search service includes only definitions of type Text.

## Transactional/service-enforced invariants

These require later shared services; the database model alone is not a product authorization or graph rules engine:

- Construct trusted owner/human/credential/system actors; check current plugin expiry/revocation and current project grants/scopes on each request, including every query/count/search branch. Validate optional actor user IDs against the owner and reject forged attribution. No browser/agent database credentials and no RLS claim.
- Lock the affected `projects` row with `SELECT ... FOR UPDATE` as the structural guard before section/task hierarchy or dependency validation. Validate full section subtree depth <=3 and acyclicity; one task nesting level; null-safe parent/child section equality; no dependency cycles or parent/subtask dependency edges. Move parent/subtasks atomically. Project ownership, task project/number and prefix remain immutable.
- Allocate/increment `next_task_number` transactionally; never decrement/reuse numbers after deletion. The SQL uniqueness constraint is the final collision guard. Keep gapped positions within the documented local scope and rebalance only that scope.
- Maintain all six workflow categories and exactly one Backlog default; immutable status categories; confirm/remap populated status removals and GitHub rule targets. SQL enforces at most one default, not existence.
- Normalize label/definition/option names consistently before writes (Unicode NFKC, trim, collapse whitespace and locale-independent lowercase); SQL enforces uniqueness of the resulting nonblank key. Validate Unicode-aware name/text limits, colors, finite numbers, valid calendar dates, http/https URLs, and owner timezone. Keep property type immutable; serialize the 30-definition/50-option limits under the project guard. Scalar column choice must match the definition type; Multi-select uses selection rows only. Confirm destructive property changes with affected task counts, including archived tasks.
- Use expected-revision predicates and increment revision/update `updated_at` explicitly. Mutation, activity, property edits, note revision insertion/pruning, idempotency result and durable enqueue commit in one transaction. Timestamps/revisions are not SQL update triggers.
- Validate supported bounded rich-text JSON, derive plain text, retain the last 20 content revisions, and append a fresh revision on restore. The database does not parse Tiptap nodes or prune history.
- Compute effective archive through ancestors, leaf progress, unresolved parents, timezone-relative overdue and dependency satisfaction. Enforce explicit completion/reopening/archive choices without partial mutations; owner-only permanent deletion requires archived work and confirmation. Block deletion while surviving tasks depend on the deletion set.
- Validate upload media/bytes, finalize readiness through the documented state machine, authorize downloads and clean abandoned/rejected bytes. Enqueue immutable object keys durably before local cascading deletes. SQL cannot delete external bytes.
- Require a currently connected/available repository for new links/imports, issue-only import, and provider/project authorization. Persist provenance independently of visible links/membership; repository disconnection must not erase historical context. Rule/link baselines and event fingerprints suppress historical replay; compare remote versions before cache writes; require complete verified PR sets, qualifying post-baseline events and current task revision/category before transitions.
- Atomically claim jobs with row locks/`SKIP LOCKED`, a fresh lease token and bounded attempts; fence completion/retries by that token. Coalesce/reschedule the existing deduplication row, or use a new operation-specific deduplication key. Keep payloads minimal and secret-free; never hold transactions during provider requests.
- Derive idempotency identity from the server actor, compare fingerprints, cache successful authorized results only, and remove expired records before accepting a reused key. Default retention is 24 hours. Give completed export artifacts 24 hours' availability, redact auth/secret data, and queue expiry deletion. Defaults on creation do not replace completion/expiry scheduling.

## Deletion and retention

| Records | Deliberate deletion behavior |
| --- | --- |
| Project/section/task-owned work | Composite parent FKs enforce scope and cascade local descendants, associations, notes and file metadata. A prerequisite reference uses nondeferrable `NO ACTION`: incoming dependency edges must be removed before or by the deletion statement; surviving dependent edges block it. Services must compute the deletion set and order their statements accordingly. |
| Notes/revisions | Target deletion cascades note and saved revisions. Routine revision pruning is a service transaction; notes do not leave orphaned content. |
| Activities | Project deletion removes its activities. Section/task target IDs are historical logical references without FKs, so surviving project activity retains deleted-target IDs and safe changed-field summaries. Services validate the owner/project of live targets on insertion. |
| Credentials/auth | Plugin key deletion sets credential `api_key_id` to null; the credential identity remains for audit. Activity/note revision/file/idempotency references restrict deleting referenced credentials. Revocation uses plugin state, not deleting audit identity. Domain data/jobs restrict owner deletion; no account-deletion product is introduced. |
| GitHub | Unlinking deletes only the visible link. Import provenance cascades only with its task/project; permanent deletion permits a deliberate fresh import. Provider items/repos/installations are retained with availability/status markers; restrictive FKs preserve provenance and tasks through provider access loss. Rules/evaluations cascade with project/task ownership. |
| Jobs/exports/idempotency | No cascading project/task/file FK in job payloads or result snapshots. A durably queued object deletion survives its local target. Jobs remain through retries/terminal diagnosis; exports retain object keys for expiry cleanup. Cleanup/retention is performed by later bounded handlers. |

Use forward fixes for migrations; destructive changes need a backup and explicit recovery plan. `tests/support/postgres.ts` creates a unique guarded local test database, applies the committed journal, exposes a repeatable migration runner for future upgrade cases, and closes/drops the database in teardown. Future upgrade tests should load a prior migration prefix plus a representative prior-version fixture, apply the remaining journal, and assert preservation. No destructive down-migration is promised. The initial test covers journal idempotence; there is no earlier released schema to upgrade yet.
